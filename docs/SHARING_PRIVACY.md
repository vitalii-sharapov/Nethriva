# Shared libraries, external credentials and privacy lock

These implementations of roadmap 21–23 are included in the [0.13.0 preview, build 30](releases/0.13.0.md). They do not create a hosted service, publish private files, install a password manager, or change existing saved clients automatically.

## Shared connection libraries

Open **File → Shared Connection Libraries…**. Select network clients, name the library and choose **Save New Shared File…**. Review the exact clients and groups before saving a new `.nethriva-shared` file. Existing files are never overwritten. Local Terminal and Serial are intentionally excluded because they describe this Mac rather than a shared network destination.

The strict allowlist contains library/client identifiers, names, protocols, hosts, ports, group paths and virtualization platform. It does **not** include usernames, domains, individual passwords, credential-profile identifiers, provider references/tokens, SSH identity paths/jump chains, commands, personal terminal settings, clipboard/device redirection or certificate bypasses. By default, only selected clients’ groups and ancestors are included; **Include all groups, including empty ones** explicitly adds the entire group structure. Files still reveal infrastructure, so share only with intended recipients and protect the shared folder. Files are created with owner-only permissions (0600); configure access/sharing deliberately outside the app.

Choose **Link Shared File…** to review/import another library. Import creates separate local UUIDs with no credentials or inherited rules. Attach your own account/profile afterwards. Imported RDP clients start with strict certificate checking and clipboard sharing disabled. Other protocol-specific options remain safe defaults; configure private key/jump paths and platform-specific settings locally.

**Refresh & Review** reads a linked file manually. A local baseline supports a field-level three-way merge for name, protocol, host, port, group and platform. Unchanged personal fields receive incoming edits; personal-only edits remain overrides; conflicting edits ask which value to keep, with **keep personal** as the default. Changed destinations always require review even without a conflicting personal edit. Accepting a different host/port/protocol/platform creates a fresh, credential-free client and keeps the former client independent—never silently retargeting its password. A group move freezes old opt-in inherited settings, preventing the new group from supplying another personal credential implicitly.

Shared removals keep local clients rather than deleting their passwords. Locally deleted clients are not resurrected while their mapping remains linked. Existing live tabs keep their snapshots. **Unlink** removes tracking only, not clients or Keychain items. Merging checks the file fingerprint, exact local records and baseline again after preview; stale previews are rejected. Shared files have bounded reads and reject unknown fields, duplicate client IDs, symlinks and unsupported schema versions. Local link corruption is preserved and disables saving rather than replacing the tracking data.

**Save New Revision…** creates a reviewed new file with the same library/client identities, using current linked clients plus any additionally selected clients. Personal metadata edits are deliberately included in that preview; credentials and private options are still excluded. Give teammates the new file; they choose **Link Shared File…** to merge it against their old baseline. No automatic polling, cloud upload, shared-file replacement, distributed locking or server-side permissions are provided. A write error can leave an incomplete newly created file; discard/re-create that copy before sharing it. Normal `.nethriva`/encrypted archives remain separate backup formats, not shared tracking files.

## External credential providers

Create/save a named profile in **File → Manage Credential Profiles…** first. Its username and optional RDP domain remain local metadata. Expand **External credential provider**, enable the option and save the provider choice. Link clients through the existing Credentials picker. New SSH/SFTP, Telnet, RDP or VM sessions fetch the referenced password asynchronously when needed; existing session copies are not rotated automatically.

- **1Password CLI:** install the official `op` executable in one of the offered standard locations; enable desktop-app integration and enter a password-field reference such as `op://vault/item/password`. The desktop app handles approval. Nethriva runs only `op read --no-newline` with a fixed argument list, no shell, credential environment or service-account token. stdout is a bounded private pipe; stderr is discarded and errors never display the provider response. The request is cancelled on tab close/lock and has a 60-second deadline. This requires an existing 1Password account/application and supported CLI setup; Nethriva does not register one for you. See [official CLI read](https://developer.1password.com/docs/cli/reference/commands/read/) and [desktop integration setup](https://developer.1password.com/docs/cli/app-integration/).
- **HashiCorp Vault KV v2:** enter an HTTPS server, `mount/path`, password-field key and optional enterprise namespace. Save those settings, then enter a short-lived token into the secure field and choose **Authorize for This App Session**. A bounded ephemeral HTTPS request reads `/v1/<mount>/data/<path>` and extracts just the selected string field. System certificate validation is required; redirects, shared cookies/HTTP credentials and insecure certificate exceptions are not used. Tokens are memory-only, cleared on lock, explicit Forget Authorization, profile change or quit. Vault ACLs, token lifetime and KV version must permit the read; there is no OIDC/LDAP login UI, KV v1 or automatic token renewal. See [official KV v2 API](https://developer.hashicorp.com/vault/api-docs/secret/kv/kv-v2).

**Test Read (No Password Display)** requests the configured field without showing/saving it. A provider choice overrides an old Keychain password without deleting it; remove the old saved password explicitly if desired. Provider passwords are not copied into Keychain or credential exports. Provider configuration is kept separately in the active local Debug/Release profile and excluded from all connection/shared archives; imported profiles must be configured/authorized separately on another Mac. **Forget Vault Authorization** clears temporary tokens and cancels pending reads, including results arriving late. Bitwarden and other providers are not implemented in this iteration. Local provider references may themselves reveal vault/item names and should be treated as private metadata.

Password fields must be nonempty single-line UTF-8 strings up to 64 KiB without control characters. This deliberately excludes private-key documents/notes and prevents multiline provider content being injected into a terminal password prompt.

## Privacy lock

Choose **File → Lock & Disconnect Sessions**, press **Command-Shift-L**, or use **Settings → Privacy Lock**. Unlock through the visible button with macOS LocalAuthentication: **Touch ID or the Mac login password**, not a remote-client password. Failed/cancelled authentication and stale callbacks leave the app locked. Lock state persists across quitting/restarting; it is separate in Debug, Release and test profiles.

Locking conceals the main workspace, detached sessions and other Nethriva windows using native shields, hides their underlying accessibility content/titles and blocks terminal command routing and credential access. It closes live tabs, stops output recording, cancels remote-editor operations while keeping unsaved buffers, stops owned tunnels, closes app-owned SSH masters, and clears temporary VM logins/Vault tokens/pending provider reads. Unlock waits for owned SSH shutdown; the control directory remains available for subsequent connections. Reopen clients explicitly after unlocking—there is no command, transfer, VM action or session replay.

Optional **Lock when Mac sleeps or its screen locks** and **Lock after no activity in Nethriva** (5/15/30/60 minutes) are off by default. Activity means local input in Nethriva, not ongoing remote output. Long-running remote commands/uploads may have already reached a host before disconnect/cancel; verify their outcome before retrying. Unsaved remote-editor text remains in process memory and becomes accessible again only after unlock; quitting with unsaved edits requires unlocking to answer the discard confirmation.

This is an application privacy boundary, not disk encryption, secure memory erasure or protection against another process running as the same Mac user. It does not clear the system clipboard, delete existing logs/backups, hide files in Finder, revoke external vault tokens at their issuer, or sign you out of the 1Password desktop app. Use macOS screen locking/FileVault and normal vault controls for those threats. Restarted sessions may still reuse your configured SSH agent after authentication; no credentials are embedded in the app bundle.

SSH master/forward shutdown requests can lose their acknowledgement after a socket or connection change; an already-ended master can also return failure. A fixed notice or Tunnel Manager status warns when closure is unconfirmed. After unlocking, check that status and the host rather than assuming every forward stopped. The lock closes Nethriva session surfaces and gates its credentials; it is not an operating-system network revocation mechanism.

## Acceptance checks

Use synthetic libraries/disposable sessions; never attach real archives, tokens or raw provider errors to an issue.

1. Export a selected shared library and verify excluded usernames/profiles/keys; explicitly test optional empty groups. Link it into another development profile and assign a personal profile there.
2. Edit name/group on both sides, distribute a same-identity revision, review conflicts and verify the selected outcome. Test an endpoint change: the old credential-bearing client remains unchanged and the new one has no saved credentials.
3. Delete a shared/local client and verify non-destructive unlink/tombstone behavior. Change the file or a client after preview and confirm the merge is rejected; existing tabs must stay unchanged.
4. Configure a synthetic 1Password item or test Vault KV v2 entry. Test successful read, denied/expired authorization, missing item and cancellation; no secret should appear in UI, preferences, logs or exports. Official provider interoperability still needs user setup/acceptance.
5. Open multiple windows, detached/local sessions and an editor, then lock. Confirm no content/title/accessibility disclosure, no terminal input or credential reads, recording stopped and network sessions disconnected. Cancel Mac authentication, try again, unlock, and reconnect explicitly. Test restart while locked plus optional sleep/idle locking. Actual Touch ID/password behavior requires user validation on the Mac; automated tests use a fake authenticator, never personal credentials.
